# TMTWINCD.EXE code segments 1058–1090: graphics core, font, screen effects, menus, dialogs, wave sound, MIDI music

Scope: every function whose entry point is in Ghidra selectors `1058`, `1060`, `1068`, `1070`, `1078`, `1080`,
`1088` and `1090` of `TMTWINCD.EXE` (NE segments 12–19). That covers 88 Ghidra functions plus 3 entry points Ghidra
did not turn into functions (`1058:0776`, `1068:00d5`, `1090:03e6`) and the jump-table tails of two dialog procs
(`1080:02c2..02f9` and `1080:0350..0387`).

Evidence: `re/win/ghidra_export/{functions.tsv, functions/*.c, disassembly.asm}`, the raw EXE (segment bytes, NE
relocation and entry tables, DGROUP initialised data at file offset `0x23c00`), the EXE `NAMETABLE`/dialog resources,
and `extracted/res/TMT.DLL/32514/999` (the font). Scratch scripts are in `extracted/scratch/code_1058/`
(`nerel.py` lists far references through NE relocations, `dgrel.py` lists DGROUP relocations, `gaps.py` finds code
that Ghidra skipped, `ffnt.py` decodes the font, `dlg.py` decodes dialog templates). A second verification pass
(scratch `extracted/scratch/code_1058_v2/`, `dg.py` dumps DGROUP) re-read every decompiled function against the
disassembly and DGROUP bytes. It hand-decoded the three gap routines and the dialog jump tables, resolved four
former open questions using the companion docs (`code_1008-1030.md`, `code_1038-1050.md`, `code_10e0-10f0.md`,
`fmt_pmap.md`), and added per-segment reference tables for 1060–1090.

Notation: **[O]** = observed directly in code, bytes or decoded data. **[I]** = inference. Addresses are
`selector:offset`. `DGROUP:x` (also written `DAT_11b8_x`) means DGROUP offset x, at file offset `0x23c00+x`.
All multi-byte values are little-endian (x86). "16-colour mode" and "256-colour mode" refer to `g_paletteDevice`
(`DGROUP:086c`) being 0 or non-zero. "WinG mode" means `DGROUP:0074` is non-zero (set in `1018:086d` from the INI
`UseWinG` key).

## 1. Module map

Each segment is one source module. The DGROUP data that each module owns is laid out in segment order, which
confirms the module boundaries [O]. No segment in this range contains C++ classes. There are no constructors,
destructors, vtables or `this` pointers. All functions are plain `cdecl far` C functions, apart from the four
exported `FAR PASCAL` dialog procedures in 1080 [O].

## 2. Shared data structures

### 2.1 Offscreen framebuffer [O]

The game draws everything into one offscreen buffer that is **512 pixels wide and 1055 (0x41f) rows tall**.
Only rows 0..383 are ever presented, as a 512×384 "screen" (the Mac edition's resolution). The rest of the
buffer holds two more layers stacked below the screen:

| Rows | Layer | Evidence [O] |
|---|---|---|
| 0..383 | Composed frame. This is the only part that `Gfx_BlitToWindow` presents | `1058:05bc` clips to y < 0x180 |
| 384..767 | Back page: the room background plus static props, used to erase sprites (copy from y+384). It also saves the whole screen | `1198:0234` draws the room PMAP at (0, 0x194 = 404); `1160:00ee` saves with `0b6a(0,0,512,384 → 0,384)` |
| 788..1054 | Pristine copy of the 512×267 play-field (screen rows 20..286) | `1198:0234`: `Gfx_CopyOffscreenRect(0, 404, 512, 0x10b, 0, 0x314 = 788)` |

That explains the odd height: **1055 = 768 + 20 + 267**. The third layer stores only the play-field rows,
so it ends exactly at the last buffer row. The constants are observed; that they are the reason for the height
is an inference [I]. The dissolve reveals a
scene composed on the back page (`Screen_DissolveCopy(0, 404, 512, 267, 0, 20)` at `1198:0651`).
`Screen_Clear` clears rows 0..767 (layers 0 and 1), and `10e0:0391` sets a clip rectangle that is 768 rows
tall, so sprites can be drawn into the back page.

Setup is done by `1018:0563` and uses helpers from this module:

* `g_hdcScreen` (`DGROUP:4296`) = `GetDC(hwndMain)`; `g_hdcMem` (`4298`) = `CreateCompatibleDC(g_hdcScreen)`.
* `g_paletteDevice` (`086c`) = `GetDeviceCaps(g_hdcMem, RASTERCAPS) & RC_PALETTE` (0x100).
* Non-WinG: `g_hbmBack` (`429a`) = `Gfx_CreateSysMemBitmap(512, 1055, PLANES, BITSPIXEL)`, which is then
  selected into `g_hdcMem`. The global handle of the bitmap's bits is obtained with
  `Gdi_GetBitmapBitsHandle(g_hGdiHeap, hbm)`, a GDI-internals hack described in §4.10.
  * 256-colour: `g_selPixels` (`429e`) = `GlobalHandleToSel(bits)`. The DDB *is* the linear 8bpp buffer.
  * 16-colour: `g_selPlanarBits` (`429c`) = `GlobalHandleToSel(bits)` (planar device bitmap). In addition
    `g_selPixels` = `Gfx_AllocPacked4bpp(512, 1055)`, a separate packed 4bpp buffer of 270 080 bytes.
  * If the bits handle is 0, the `INCOMPATIBLEVIDEO` dialog is shown and start-up fails (`1018:0639`).
* WinG: `1008:00ee(512, 1055)` creates the buffer (that is in the WinG module).

Pixel addressing, as used by all blitters (huge or 32-bit offsets from `g_selPixels`):

| Mode | Bytes per row | Address of (x,y) | Pixel packing |
|---|---|---|---|
| 256-colour / WinG | 512 | `y*512 + x` | 1 byte = system-palette index |
| 16-colour | 256 | `y*256 + x/2` | high nibble = even (left) x, low nibble = odd x; value = 4-bit device colour |

On presentation, the 16-colour packed rectangle is first converted into the planar DDB by `1050:09e7`.

Presentation geometry: the game area is drawn at client position (`g_viewOriginX`, `g_viewOriginY`) = (`DGROUP:086e`,
`0870`). These values are computed by `1018:0115`, which centres the area and rounds x down to a multiple of 4. The
client area outside 512×384 is painted black by `Gfx_PaintWindowBorders`.

### 2.2 PixMap (PMAP resources and in-memory images) [O]

```
struct PixMap {            // far pointer, may span >64 KB (huge arithmetic)
    int16  width;          // +0
    int16  height;         // +2
    uint8  data[];         // +4
};
```
`data` has one of three layouts:

| Form | Where it occurs | `data` |
|---|---|---|
| Raw 8bpp | TMT256 PMAPs that are not compressed, save-under buffers (256-colour), unpacked temporaries | `width*height` bytes, rows top-down, no padding |
| Raw 4bpp | TMT16 PMAPs, save-under buffers (16-colour) | `ceil(width/2)` bytes per row, high nibble first |
| RUND 8bpp | TMT256 PMAPs | `"RUND"` (4 ASCII bytes) followed by RLE packets (§4.5) |

`PixMap_IsRUND(pm)` is `_fmemcmp(pm+4, "RUND", 4) == 0` (string at `DGROUP:0997`). RUND is never produced or
expected in 16-colour mode (the RUND draw routines are 8bpp-only) [I: TMT16 data is never RUND].

In 256-colour mode every PMAP is remapped in place into system-palette indices right after loading
(`PixMap_RemapToSystem`, which `1038:03da`/`1038:0ba8` call; see §4.7). Pixel values in memory are therefore
device indices, not RRGB indices.

### 2.3 Rectangles

* `RECT` = Win16 `{int16 left, top, right, bottom}` with right and bottom exclusive. `Rect_SetXYWH(r,x,y,w,h)`
  gives `{x, y, x+w, y+h}` [O].
* `DirtyRect` = `{int16 x, y, w, h}`. `g_dirtyRects[256]` is at `DGROUP:42a2` (8 bytes each, up to `4aa1`), and
  the count is `g_dirtyCount` (`0874`) [O].
* The **clip rectangle** used by the transparent PixMap blits is *inclusive*: `g_clipLeft` (`0868`),
  `g_clipTop` (`0864`), `g_clipRight` (`086a`), `g_clipBottom` (`0866`). The initial data values are
  0/0/0x200/0x180. Scene code sets `{0,0,0x1ff,0x17f}` (`10c8:0000`), `{0, off+0x14, 0x1ff, off+0x11e}`
  (`10e0:036b`, the 512×267 play-field below a 20-pixel top band) or `{0,0,0x1ff,0x2ff}` (`10e0:0391`) [O].

### 2.4 Colour model (owned by 1048, used here) [O]

* **Logical colours 0..15**. RGB table `DGROUP:07d8`, 16 entries × `{u16 r, u16 g, u16 b}` (6 bytes):
  0 (0,0,0) · 1 (0,0,AA) · 2 (0,AA,0) · 3 (0,AA,AA) · 4 (AA,0,0) · 5 (AA,0,AA) · 6 (AA,55,0) · 7 (C0,C0,C0) ·
  8 (55,55,55) · 9 (55,55,FF) · 10 (55,FF,55) · 11 (55,FF,FF) · 12 (FF,55,55) · 13 (FF,55,FF) · 14 (FF,FF,55) ·
  15 (FF,FF,FF).
* **16-colour device values**: `DGROUP:0838`, `u16[16]` = `0,4,2,6,1,5,1,8,7,12,10,14,9,13,11,15`. This is the
  logical colour mapped to the 4-bit value stored in the packed buffer. The 8/7 swap and brown→1 are as found.
* **256-colour device value** of logical colour c =
  `GetNearestPaletteIndex(hpal, PALETTERGB(r,g,b))` (COLORREF `0x02bbggrr`). `hpal` is either the game palette
  `DGROUP:07d4` or a temporary palette built from the current system palette (`1048:0034`).
* **Current colour**: `1048:02fd(c)` stores c in `DGROUP:4293` (returned by `1048:03bb`) and the device value in
  `DGROUP:4191` ("pen pixel", used by the glyph blitters).
* **Transparent key**: `DGROUP:4190` (byte). The default, set by `1048:008b`, is nearest(RGB 0,0,0xAA) in
  256-colour mode and 3 in 16-colour mode. `1048:00b7(r,g,b)` sets it to nearest(r,g,b), or 15 in 16-colour mode.
* **System remap table** `DGROUP:4193..4292` (`u8[256]`), built by `1048:010a` after `SetPaletteEntries`
  and `RealizePalette`: game-palette index → nearest system-palette index. The same routine then remaps
  `g_shadowTable` (`1048:03bf`).

### 2.5 FFNT bitmap font (TMT.DLL type 32514, id 999) [O]

```
u8  unused;            // +0  (0)
u8  lastChar;          // +1  n = lastChar+1 glyphs (0xff -> 256)
u8  height;            // +2  rows per glyph (0x11 = 17)
u8  width[n];          // +3  advance width = bitmap width in pixels, spacing included
u8  offLo[n];          // +3+n      glyph offset, low byte
u8  offHi[n];          // +3+2n     glyph offset, high byte
u8  bits[];            // +3+3n     glyph c at bits[offHi[c]<<8 | offLo[c]]
```
Each glyph has `height` rows of `ceil(width/8)` bytes. The MSB is the leftmost pixel and rows are not padded
further. For id 999 all 256 offsets are consistent and the bitmap data is 7718 bytes (checked with `ffnt.py`).
Set bits are drawn in the current pen colour and clear bits are transparent.

### 2.6 Remap "spec" [O]

`u8 n; struct { u8 newValue; u8 oldValue; } pair[n];`. `Remap_BuildTable` turns it into a 256-byte table:
identity, then `table[old] = new` for each pair in order.

### 2.7 Menu definitions (1078) [O]

```
struct MenuBarDef {              // e.g. DGROUP:13bf
    int16          count;        // +0  number of top-level menus (3)
    MenuDef far*   menus;        // +2  array of count entries (DGROUP:1383)
};
struct MenuDef {                 // 20 bytes
    char far*      title;        // +0x00  "&File"
    int16          unk4;         // +0x04  0x3f / 0x4e / 0x42 (not used by 1078)
    int16          itemCount;    // +0x06
    char far*      items;        // +0x08  '\n'-separated item texts, modified in place ('\n'->'\0')
    void (far* far* handlers)(void); // +0x0c  array[itemCount] of far handlers (NULL = no action)
    int16          unk10, unk12; // +0x10  0x84,0x46 / 0x81,0x88 / 0x8f,0x01 (not used)
};
```
The game's single menu bar (`DGROUP:13bf`, installed by `1120:0000`; `1120:000d` removes it) has these entries:

| Menu | Items → handler |
|---|---|
| File (3) | item 0 → `10f0:0487` (shows rank screen), item 1 → `1140:0062`, item 2 → `1140:0098` |
| Options (3) | → `1140:0015`, `1140:00cc`, `1140:00f7` |
| Help (5) | → `1180:0117`, `1180:0128`, `1180:0139`, `1180:014a`, `1140:0000` |

(The item texts are in DGROUP `0x1317`, `0x134d` and `0x12a0`.)
Command id = `menuIndex*256 + itemIndex`.

## 4. Segment 1058: graphics core

### 4.1 Presentation and dirty rectangles

**`Gfx_BlitToWindow(x, y, w, h)`** at `1058:05bc` [O]
1. If x<0, then w -= |x| and x = 0. If y<0, then h -= |y| and y = 0.
2. If x+w > 512, then w = 512−x. If y+h > 384, then h = 384−y.
3. If w ≤ 0 or h ≤ 0, return.
4. WinG mode: call `1008:02b6(struct{int16 x,y,w,h} by value)`. The 8-byte struct is built at `bp-8` and
   pushed with `F_SPUSH@` (CX = 8) (`1058:0622..0641`). Note that it is x/y/width/height, not a Win16 RECT.
   Otherwise: in 16-colour mode first `1050:09e7(x,y,w,h)` (packed 4bpp → planar DDB), then
   `BitBlt(g_hdcScreen, g_viewOriginX+x, g_viewOriginY+y, w, h, g_hdcMem, x, y, SRCCOPY)`.

**`Gfx_AddDirtyRect(x,y,w,h)`** at `1058:068e` [O]: does nothing unless `g_dirtyEnabled != 0` and
`g_dirtyCount < 256`. The rectangle is clipped exactly as in steps 1–3 above and, if it is still non-empty, appended.
Overflowing rectangles are silently dropped.

**`Gfx_FlushDirtyRects()`** at `1058:0731` calls `Gfx_BlitToWindow` for every entry in order and then sets
`g_dirtyCount = 0`. **`Gfx_ClearDirtyRects()`** at `1058:076f` only resets the count. Rectangles are not merged or
de-duplicated.

`1058:0776` (no Ghidra function, never referenced) is `Gfx_BlitToWindow(0,0,512,384)`.

**`Gfx_BlitRectToWindow(RECT far*)`** at `1058:0788` calls `Gfx_BlitToWindow(l, t, r−l, b−t)`. In WM_PAINT
(case starting near `1010:020a`) the window procedure first calls `Gfx_PaintWindowBorders()` (far call at
`1010:021c`, found through an NE relocation) and then
`IntersectRect(ps.rcPaint, {viewX, viewY, viewX+512, viewY+384})`. It offsets the result by (−viewX, −viewY) and
passes it here (far call at `1010:0274`) [O].

**`Gfx_PaintWindowBorders()`** at `1058:1578` [O] calls `GetClientRect(hwndMain, rc)` and takes
`br = GetStockObject(BLACK_BRUSH)`. It then calls `FillRect(g_hdcScreen, …, br)` for four bands:
`(0,0)-(rc.right, viewY)`, `(0,viewY)-(viewX, rc.bottom)`, `(viewX+512, viewY)-(rc.right, rc.bottom)` and
`(viewX, viewY+384)-(viewX+512, rc.bottom)`.

### 4.2 Solid fills, frames, lines and pixels [O]

**`Gfx_FillRectColor(RECT far* r, int c)`** at `1058:07d0` fills the rectangle with logical colour c:
* WinG: `1008:0418(r, c)`.
* 256-colour: `idx = GetNearestPaletteIndex(g_hPal(07d4), PALETTERGB(rgb[c]))`. It creates
  `brush = CreateSolidBrush(PALETTEINDEX(idx))`, selects it into `g_hdcMem`, calls `FillRect(g_hdcMem, r, brush)`,
  restores the old brush and deletes the new one. Clipping is GDI's (to the 512×1055 bitmap).
* 16-colour: copies the RECT. If right==left it sets right++, and if bottom==top it sets bottom++. It then calls
  `1050:097c(left, top, right−left, bottom−top, dev16[c])` (nibble fill, **no clipping**).

These wrappers use the current colour (`1048:03bb`):
`Gfx_DrawPixel(x,y)` (`08d8`) fills {x,y,1,1}; `Gfx_DrawHLine(x,y,w)` (`090f`) fills {x,y,w,1};
`Gfx_DrawVLine(x,y,h)` (`0947`) fills {x,y,1,h}; `Gfx_FillRect(x,y,w,h)` (`097f`) fills {x,y,w,h}.

**`Gfx_FrameRectColor(RECT far* r, int c)`** at `1058:09b8` draws a one-pixel outline:
* WinG: `1008:050b(r,c)`.
* 256-colour: GDI `FrameRect` with the same palette brush as above.
* 16-colour: four `1050:097c` fills with `L,T,R,B` = r:
  top `(L, T, R−L+1, 1)`, left `(L, T, 1, B−T+1)`, right `(R−1, T, 1, B−T)`, bottom `(L, B−1, R−L, 1)`.
  The top and left strokes are one pixel longer than GDI's (they reach column R and row B). This is a quirk.

`Gfx_FrameRect(x,y,w,h)` (`0b31`) calls `Gfx_FrameRectColor({x,y,w,h}, current colour)`.

### 4.3 Copying inside the framebuffer [O]

**`Gfx_CopyOffscreenRect(sx, sy, w, h, dx, dy)`** at `1058:0b6a` first calls `Gfx_AddDirtyRect(dx, dy, w, h)`. It
then copies the block, using `1050:0899` (8bpp, `memcpy` per row, pitch 512) or `1050:0732` (4bpp, handles all four

### 4.5 RUND run-length codec (exact) [O]

Packed layout: `int16 w, int16 h, "RUND", packets…`. The pixel stream is the `w*h` raw 8bpp pixels, row-major.

**Decoder** `PixMap_UnpackRUND(src, dst)` at `1058:0400`:
```
copy src[0..3] -> dst[0..3]            // w, h
si = 8; di = 4; end = w*h + 4          // 32-bit arithmetic
while di < end:
    b = src[si]; n = b & 0x7f
    if b & 0x80:  v = src[si+1]; si += 2; repeat n: dst[di++] = v      // run
    else:         si += 1; repeat n: dst[di++] = src[si++]            // literal
return si                               // compressed bytes consumed (incl. 8-byte header)
```
The decoder does not bound-check against `end` inside a packet. A well-formed stream never overshoots. `n = 0` is a
legal no-op packet.

**Encoder** `PixMap_PackRUND(src, dst)` at `1058:0000`. It is only used by dead code, but defines the format.
Indices into `src` include the 4-byte header, so pixels are `src[4 .. N+3]` with `N = w*h` and `T = N+4`:
```
dst[0..3] = src[0..3]; dst[4..7] = "RUND"; o = 8; i = 4
run4(i) := i < N-1 && src[i]==src[i+1]==src[i+2]==src[i+3]
while i < T:
    ctl = o++
    if run4(i):
        v = src[i]; dst[o++] = v; i++; n = 1
        while n < 127 && i < T && src[i] == v: n++, i++
        dst[ctl] = 0x80 | n
    else:
        n = 0
        while n < 127 && i < T && !run4(i): dst[o++] = src[i++]; n++
        dst[ctl] = n
return o                                 // packed size
```
A run is started only when at least 4 equal pixels follow and the position is before the last 5 pixels
(`i < N−1`). Maximum packet length is 127.

`PixMap_UnpackedSize(pm)` (`0c1e`) = `(int32)w*h + 4` (via `F_LXMUL@`).

### 4.7 Colour remapping [O]

* **Load-time palette remap** `PixMap_RemapToSystem(pm)` (`1d28`), called from `1038:0444`/`0c22` for PMAPs in
  256-colour mode. For RUND it calls `PixMap_RemapRUND` (`1c1b`), which walks the packets and replaces each run
  value and each literal byte b with `g_palRemap[b]` (`DGROUP:4193`) until w*h pixels are covered. For raw pixmaps
  `1050:0b36` replaces all w*h data bytes. The header and packet control bytes are untouched.
* **`Gfx_HighlightRect(x, y, w, h)`** (`19b2`), used by `1150:0dcd`/`0e14` with h = font height to highlight a
  word or line. It builds a 256-entry table and remaps the framebuffer rectangle through it (`1050:0db5` per byte,
  or `1050:0cfa` per nibble):
  * every value → colour 14 (yellow)
  * dev(0 black) → dev(1 blue)
  * dev(4 red) → dev(6 brown)
  * dev(14 yellow) → dev(1 blue)

  These are applied in this order, so later entries override earlier ones. "dev" means `dev16[]` in 16-colour
  mode and nearest-system-index in 256-colour mode. The transformation is not an involution, so the region must
  be redrawn to un-highlight it [I].
* `Gfx_RemapRect(x,y,w,h,spec)` (`1825`) remaps a rectangle through a spec table (§2.6). Its only caller is the
  dead `Gfx_InvertRect16` (`187f`), which uses the template at `0976` with pairs `(new=dev(15−i), old=dev(i))`
  for i = 0..15. That is Mac `InvertRect` for the 16 standard colours.
* Dead helpers: `Remap_BuildTable` (`16b5`), `Remap_ApplyToBytes` (`1712`), `PixMap_RemapColors(pm, spec)`
  (`174b`) and `PixMap_ReplaceColor(pm, from, to)` (`13be`). For RUND input the last two unpack, modify, repack into
  the *original* buffer with `PixMap_PackRUND`, and do not free the temporary buffer when the new packed size
  exceeds the old one. That is a leak, and the original buffer has already been overrun at that point [O].

## 5. Segments 1060 and 1068: bitmap font

**Selecting a font** `Font_Select(slot)` (`1068:0073`) [O]. With `p = g_fonts[slot]` and `n = p[1]+1` it sets
`g_curFont = slot`, `g_fontSeg = seg(p)`, `g_fontHeight = p[2]`, `g_fontWidths = off(p)+3`,
`g_fontOffLo = widths+n`, `g_fontOffHi = offLo+n` and `g_fontBits = offHi+n`.

* `Font_Load(resId, slot)` (`1068:0000`): `g_fonts[slot] = Res_LoadCopy("FFNT", resId)` (`1038:03da`).
* `Font_Init()` (`1068:0024`, from `1010:00af`): `Font_Load(999, 0); Font_Select(0)`.
* `Font_Free(slot)` (`1068:0039`): `DisposePtrDeep(g_fonts[slot])` and clears the slot.
  `Font_Shutdown()` (`1068:006b`, from `1010:00b9`) calls `Font_Free(0)`.
* `Font_GetHeight()` (`1068:00d9`) and `Font_CharWidth(ch)` (`1068:00dd` → `1060:02e4`) read the cached table.
  `1068:00d5` (no Ghidra function, unreferenced) returns `g_curFont`.
* `Font_DrawChar(x, y, ch)` (`1068:00f6`) calls `1060:0000` in 16-colour mode or `1060:01ef` in 256-colour mode,
  and returns the glyph width.

**Glyph blit** (`1060:0000` 4bpp, `1060:01ef` 8bpp), hand-written assembly [O]. It uses
`src = g_fontSeg : g_fontBits + (offHi[ch]<<8 | offLo[ch])`, `w = widths[ch]` and `rows = g_fontHeight`.
* 8bpp: `dst = y*g_rowPitch + x`. For each row, for each source byte (MSB first), each set bit writes the byte
  `g_penPixel` (`DGROUP:4191`), stopping after w pixels. The next row starts at `dst += 512` and the next source
  byte.
* 4bpp: `dst = y*256 + x/2`. Set bits write `pen<<4` into the high nibble (even x) or `pen&15` into the low nibble
  (odd x). Odd starting x is a separate code path. The row advance is `(g_rowPitch+1)>>1` = 256.
* Clear bits leave the destination unchanged. There is **no clipping** and **no dirty-rect registration**: callers
  handle both. The return value is w.

String layout (kerning, line breaking) is done by the callers in other segments, e.g. `1150`.

Implementation notes on the assembly [O]:
* Both blitters start with `ENTER 4,0` and save ESI/EDI/DS. They load ES = `g_fontSeg` to read the tables,
  then ES = `g_selPixels` (`DGROUP:429e`) for the destination, and DS = the font segment for `LODSB`. The
  destination is addressed with 32-bit `ES:[EDI]`, which needs a selector whose limit covers the whole buffer.
* The glyph offset is computed in 16 bits (`SI = g_fontBits + (offHi<<8 | offLo)`, with no carry into the
  segment). A font must therefore fit in one 64 KB segment.
* A row runs until CL (= width) reaches 0. When CL reaches 0 in the middle of a source byte, the remaining bits
  of that byte are ignored and the next row starts at the next source byte. This is the `ceil(w/8)` row stride.
* 4bpp even-x path (`1060:005d`): bit 7 → high nibble (`AND 0x0F; OR pen<<4`), bit 6 → low nibble
  (`AND 0xF0; OR pen&15`), then EDI++. The odd-x path (`1060:0129`) starts with the low nibble.
* The return value is AX = width (BL).

**`Screen_Clear()`** (`1070:0000`, from `1010:00c3` and `1018:07e1`) [O]: `1048:02fd(0)` (current colour = black),

**`Screen_DissolveCopy(sx, sy, w, h, dx, dy)`** (`1070:002d`) [O]. Its only call is
`(0, 404, 512, 267, 0, 20)` at `1198:0651`, which reveals a scene prepared in staging rows over the play-field.
```
for pass in 0..15:
    for row in 0, 2, 4, … while row < h:
        col = -g_dissolveRowShift[row % 16]
        while col < w - 2:
            c = g_dissolveColOrder[pass] + col
            if 0 <= c < w - 2:
                Gfx_CopyOffscreenRect(sx + c, sy + row, 2, 2, dx + c, dy + row)
            col += 16
    Gfx_BlitToWindow(dx, dy, w, h)
Gfx_CopyOffscreenRect(sx, sy, w, h, dx, dy)      // completes the last 2 columns and any gaps
Gfx_BlitToWindow(dx, dy, w, h)
```
`g_dissolveColOrder` is a permutation of 0..15, so in each pass every 16-pixel span of a row pair receives one 2×2
cell at a pseudo-random phase. Over 16 passes all phases are covered. There is no explicit delay: the speed was
bounded by 17 full-rectangle blits [O]. A port should pace it, for example one pass per frame [I]. Dirty
rectangles are also queued if `g_dirtyEnabled` is set, up to the limit of 256.

**Fade stubs** (`1070:011c`, `1070:0120`): both are `int f(int)` returning 1 [O]. The call pattern [O] is:
* `0120(arg)` is called before a picture is replaced and its result is tested. At `1160:023c`, a true result
  clears the screen to black instead of copying.
* `011c(arg)` is called right after a new picture has been blitted.
* The argument is −1, −2 or 0x7ffe.

They are therefore leftover Mac palette fade-out and fade-in entry points (`Fx_FadeOut_Stub`, `Fx_FadeIn_Stub`)
that do nothing in this build [I]. `1160` and `1198` call them only when `g_gfxConst4` is 3 or 4.

## 8. Segment 1080: start-up and warning dialogs

**`WinDlg_RunModal(LPCSTR name, FARPROC proc)`** (`1080:0000`) [O] sets `g_inDialog = 1` and calls `1010:05c8`
(sound suspend: if `DGROUP:049a` is set it clears it and calls `Sound_PauseAll`). It then runs
`r = DialogBox(hInst(3cda), name, hwndMain, MakeProcInstance(proc, hInst))`, frees the proc instance and calls

**Dialog procedures** (exported, `FAR PASCAL`, `RETF 0x0a`) [O]. All of them handle WM_INITDIALOG (0x110) with
`Dlg_CenterOnScreen(hDlg)` (`1080:005f`), which does a MoveWindow to the screen centre computed from SM_CXSCREEN and
SM_CYSCREEN, without repaint. WM_COMMAND (0x111) is handled as follows:

| Proc | Command handling | Return value of DialogBox |
|---|---|---|
| `OkDialogProc` (ord 2, `01b9`) | id 1 (IDOK) or 2 → `EndDialog(0)` | 0 |
| `NoMidiProc` (ord 4, `0201`) | 0xFA (Continue) → `EndDialog(IsDlgButtonChecked(0xFC) ? 1 : 0)`; 2 or 0xFB (Exit) → `EndDialog(-1)` | −1 exit, 0 continue, 1 continue + "don't check again" |
| `DesignedFor640x480Proc` (ord 5, `026c`) | Same, via a 4-entry jump table (CS:`02ea` ids `2,FA,FB,FC` → `02d3,02b7,02d3,02b5`); 0xFC is unhandled | Same |

WM_INITDIALOG → TRUE. In `OkDialogProc`, IDOK/IDCANCEL → TRUE. In the three Continue/Exit procs, Exit

the raw bytes: `02b5` is `JMP 02e0` (return FALSE), `02b7` is the Continue path, and `02d3` is the Exit path.

`MoveWindow(hDlg, (cxScreen − width)/2, (cyScreen − height)/2, width, height, FALSE)` with signed
`/2` division [O].

`Dlg_CenterOverMain` (`1080:00c1`, dead code) centres a window over the main window, or the desktop if there is no
main window. It clamps the result to the desktop and calls MoveWindow with repaint.

## 9. Segment 1088: digitised sound (waveOut)

**`Wave_Init()`** (`1088:0000`) [O]: `g_waveAvail = (waveOutGetNumDevs() != 0)`. Returns that value in AX.

**`Wave_Play(snd, startSample)`** (`1088:0014`) [O]. It does nothing unless `g_waveAvail` and `snd != NULL`. Steps:
1. `Wave_Stop()`.
2. `g_waveFmtPtr = &g_waveFmt` and fill the format: `wFormatTag=1, nChannels=1, nSamplesPerSec=snd->rate,
   nAvgBytesPerSec=snd->rate, nBlockAlign=1, wBitsPerSample=8`.
3. `waveOutOpen(&g_hWaveOut, WAVE_MAPPER (-1), &g_waveFmt, (DWORD)hwndMain, 0, CALLBACK_WINDOW (0x10000))`. The
   result is not checked.
4. Set up one WAVEHDR. `lpData` = huge(`snd + 12 + startSample`), computed with `__AHSHIFT` selector arithmetic.
   `dwBufferLength = snd->sampleCount − startSample` and `dwUser = snd`.
5. `waveOutPrepareHeader` and `waveOutWrite` (size 0x20), then `g_waveState = 1`.

Only one sound plays at a time, with no mixing. Starting a sound cuts off the previous one.

**`Wave_Stop()`** (`1088:0114`) [O]: if `g_waveAvail`:
* if open (`g_waveFmtPtr != NULL`), call `waveOutReset`, `waveOutUnprepareHeader`, `waveOutClose` and set
  `g_waveFmtPtr = NULL`;
* then loop `PeekMessage(&msg, NULL, MM_WOM_DONE (0x3bd), MM_WOM_DONE, PM_REMOVE|PM_NOYIELD)` until the queue is
  empty;
* set `g_waveState = -1`.

**`Wave_IsPlaying()`** (`1088:0175`) [O]: if a `MM_WOM_DONE` message can be removed from the queue it calls
`Wave_Stop()`. It returns `g_waveState != -1`. End of playback is therefore detected by polling the message queue.
The window procedure's own MM_WOM_DONE case (`1010:039c`) is outside this range.

**`Wave_PlayResUntilEvent(sndId, stopEvents)`** (`1088:01a9`, 7 callers, e.g. voice lines) [O]:
```
Res_LockInPlace(sndId)                 // 1038:0ba8: g_resScratch -> locked SSND
Wave_Play(g_resScratch, 0); interrupted = 0
do {
    e = PeekInputEvent()               // 1028:01f6 (does not consume)
    if e:
        for k in stopEvents until 0: if (e & 0x0fff) == k: interrupted = 1
        if e == 0x13: interrupted = 1
        if interrupted: Wave_Stop()    // the event stays queued for the caller
        else Input_GetCode()           // 1028:0131: discard any other event
} while (Wave_IsPlaying() && !interrupted)
Res_UnlockInPlace()                    // 1038:0ef8
return interrupted
```
Event codes come from `Input_GetCode` (`1028:0131`) and `Input_PeekCode` (`1028:01f6`): 0x1B for a quit or close
request, the ASCII code or `0x100|VK` for keys, and hot-spot ids with button flags (0x8000 left down,
0x4000 right down, 0x2000 right up) for the mouse (see `code_1008-1030.md` §6.3). The `& 0x0fff` comparison
removes the mouse-button flags, so a stop list entry matches a hot-spot id whichever button was used.
**0x13 is Ctrl+S.** The event fetch in 1028 toggles sound on/off (`1128:0151`) when it sees WM_CHAR 0x13, so
pressing Ctrl+S always cuts the current voice line as well [O: `code_1008-1030.md` §6.2].

`Wave_PlaySync(snd)` (`1088:023a`) is dead code: it plays the sound, busy-waits on `Wave_IsPlaying`, then stops.

## 10. Segment 1090: MIDI music (MCI sequencer)

### 10.1 Initialisation: `Midi_Init()` at `1090:0000` [O]
1. `Midi_GetSoundsDir(g_soundsDir)` (`1090:023d`): if the buffer is empty it calls
   `GetModuleFileName(hInst, buf, 0x81)`, scans back for the last `'\'` or `':'`, cuts the string after it and
   appends `"SOUNDS\"`.
2. `g_midiExtended = 1`.
3. `midiOutGetDevCaps(MIDI_MAPPER (0xffff), &caps, 0x32)`. If it returns `MMSYSERR_NODRIVER` (6), return 0.
4. Open `GetWindowsDirectory() + "\system\midimap.cfg"` with `_lopen(…, 0)`. **If the open fails, return 0.**
   `g_midiOk` stays 0 [O]. This does **not** by itself silence the music: `Midi_PlayTrack` (`1090:0388`)
   never tests `g_midiOk` and opens each track by file element, so on systems without this file music still
   plays if MCI can open the `.mid` file (code path [O], run-time result [I]; needs a run, `GAPS.md` §4 E17)
   (corrected per ARCHITECTURE.md §7.1 C18; an earlier version said music never plays).
5. Seek to offset 6 and read `u16 n`. Seek to `(n−1)*0x36 + 0x12` and read 16 bytes (the active setup's name) [I].
   Upper-case them with `toupper`. If `_fstrstr` finds any of `"ADLIB"`, `"AD LIB"`, `"MVI PRO"`, `"BAS"`,
   `"BASE"` or `"THUNDER BOARD"`, set `g_midiExtended = 0`. That selects the **B** (base, FM-synth) files; otherwise
   the **E** (extended, General MIDI) files are used. A failed first seek (result ≠ 6) or a short read skips
   this test and keeps E. The second `_llseek` result is only tested for being non-zero, so `HFILE_ERROR` (−1)
   does not skip the read. Close the file. The path buffer is 0x90 bytes (`GetWindowsDirectory(buf, 0x90)`).
6. `MCI_OPEN` with `MCI_OPEN_TYPE` (0x2000), `lpstrDeviceType = "sequencer"` → `g_seqDev`, then
   `g_midiOk = 1`.
7. `Midi_OpenTrack(9000)` (castle). Then `MCI_STATUS` with `MCI_STATUS_ITEM` (0x100) on `g_trackDev` and
   `dwItem = MCI_SEQ_STATUS_PORT` (0x4003). Then `Midi_Stop()`.
8. If the status call failed, or the returned port (low word) is not 0xFFFF (`MCI_SEQ_MAPPER`), then
   `MCI_CLOSE g_seqDev`, set `g_midiOk = 0` and return 0. Otherwise return 1.

### 10.2 Tracks [O]
* **`Midi_OpenTrack(id)`** (`02e9`): looks up `g_musicIdx` by searching `g_musicIds[0..9]`. If the id is not found
  the index becomes 10 and the tables are read out of range: callers must pass 9000..9009. It builds
  `path = g_soundsDir`, sets `g_musicFiles[idx][0] = g_midiExtended ? 'E' : 'B'` and appends the file name, giving
  for example `…\SOUNDS\Ecastle.mid`. Then `MCI_OPEN` with `MCI_OPEN_ELEMENT` (0x200, the device type follows from
  the extension), `g_trackDev = wDeviceID` and `g_midiSavedPos = 0`.
* **`Midi_PlayTrack(id)`** (`0388`, from `1128:0098`/`00e7`): if a track is open it does `MCI_CLOSE`. It calls
  `Midi_OpenTrack(id)`. If `g_trackDev != 0` and the app is active (`DGROUP:049a`), it sets `g_curMusic = id` and
  sends `MCI_PLAY` with `MCI_NOTIFY` (dwCallback = hwndMain). If the app is inactive the track is only opened. It
  starts later through `Midi_Resume`, if a pause was pending.
* **`Midi_OnPlayDone()`** (`03e6`, no Ghidra function). The window procedure calls it for `MM_MCINOTIFY` (0x3b9)
  with wParam `MCI_NOTIFY_SUCCESSFUL` (1) (`1010:0529..052e`). If `g_musicLoopPos[idx] == -1` it calls
  `Midi_Stop()`. Otherwise it sets `g_midiPaused = 1` and `g_midiSavedPos = g_musicLoopPos[idx]` (0), then calls
  `Midi_Resume()`. **The result is that every track except open1 loops forever from its start.**
* **`Midi_Stop()`** (`0413`): if a track is open it sends `MCI_STOP` (0x808) and `MCI_CLOSE` (0x804) and sets
  `g_trackDev = 0`. It always sets `g_curMusic = -1`.
* **`Midi_Pause()`** (`044b`): does nothing if already paused. A non-looping track is stopped with `Midi_Stop()`.
  Otherwise, if a track is open, it sends `MCI_STATUS` (`MCI_STATUS_ITEM`, item 2 = `MCI_STATUS_POSITION`) and
  stores `g_midiSavedPos = (int16)dwReturn`, or 0 on error. Then it sends `MCI_STOP` and sets `g_midiPaused = 1`.
* **`Midi_Resume()`** (`04bf`): if paused and a track is open, it sends
  `MCI_SEEK(MCI_WAIT|MCI_TO = 0x0a, dwTo = g_midiSavedPos)`, then `MCI_PLAY` with `MCI_NOTIFY`, and sets
  `g_midiPaused = 0`.
* **`Midi_IsPlaying()`** (`0519`): `g_curMusic != -1 && g_trackDev && g_midiOk`.
* **`Midi_Shutdown()`** (`02af`, from `1010:00cd` and the failed-init path at `1018:064d`): if `g_midiOk`, it sends
  `MCI_CLOSE` to `g_trackDev` (if open) and to `g_seqDev` (if open).
* **`Sound_PauseAll()`** (`0536`) calls `Wave_Stop()` and `Midi_Pause()`. **`Sound_ResumeAll()`** (`0540`) calls
  `Midi_Resume()`. They are called on app deactivation and activation (`1010:05c8`/`05db`), around modal dialogs
  (§8) and by `10d0`.

`Midi_OnPlayDone` at `1090:03e6` was decoded from the raw bytes (Ghidra made no function there). It has no
prologue and ends in `RETF`:
```
mov bx,[4b78]; add bx,bx; cmp word [bx+0a0e],-1; jnz L1
call 0413 (Midi_Stop); jmp L2
L1: mov word [0a4e],1; mov ax,[bx+0a0e]; mov [0a54],ax; call 04bf (Midi_Resume)
L2: retf
```

| State | `g_trackDev` | `g_curMusic` | `g_midiPaused` | Entered by |

## 13. Notes for the re-implementation

* Keep a single 512×1055 8-bit indexed framebuffer. Keep the "screen" as rows 0..383, presented at a
  centred offset in a black 640×480 (or scaled) window. Store logical PMAP pixels in RRGB-index space and drop the
  system-palette remap (`PixMap_RemapToSystem`), unless exact Windows colour collapse is wanted.
* Transparency: in 256-colour mode the key is the pixel equal to the transparent key. In the original this is
  the device index nearest to RGB(0,0,0xAA) (`1048:008b`), and white for the flagged variant (§4.4). In RRGB
  space the key is RRGB index 15 (palette 900 entries 15 and 241 are both (0,0,170), and only 15 is used by
  the art). In TMT16 data it is nibble value 3 (see `code_1038-1050.md` verification item 8 and
  `fmt_pmap.md` §6).
* Implement the dirty-rect list semantics as-is (max 256, silently dropped) or simply present the whole 512×384
  each frame. Presentation timing is driven by the callers.
* RUND: implement the decoder from §4.5 (and the encoder only if needed).
* Font: §2.5/§5. Draw with the current colour, with no clipping (add clipping defensively).
* Menus and dialogs map onto native or in-engine UI. Command ids and handler tables come from the MenuBarDef at
  `DGROUP:13bf`, which can be read at runtime from the user's EXE or rebuilt from this table.
* Music: one track at a time, looping from the start except open1 (9006). Pause and resume follow app activation
  and modal dialogs. B/E selection depends on the synthesiser, so a modern port should default to E (General MIDI).
* Sound: a single voice, 8-bit mono at the resource's rate. A new sound stops the previous one. Interruptible
  voice playback follows §9.

## Open questions

Resolved in this revision (kept here for traceability):
* *Why 1055 rows?* Answered in §2.1: 1055 = 768 + 20 + 267 (screen, back page, pristine play-field copy at
  rows 788..1054, `1198:0234`).
* *Event code 0x13?* It is Ctrl+S (WM_CHAR 0x13), which the 1028 event fetch also uses to toggle sound (§9).
* *Is the transparent key consistent with the data?* Yes. RRGB index 15/241 = (0,0,170) and TMT16 nibble 3 (§13).
* *Are `RunIn16ColorProc` and dialog `NOT_ENOUGH_FILE_HANDLES` used?* No. Their names occur only in the
  resident-name table (file offset 0x3b9) and in the NAMETABLE resource (0x2ac67). There is no DGROUP string and
  no relocation to them, so both are dead in this build [O].

Still open:
1. `g_gfxConst4` (`DGROUP:0860`, constant 4, no writer) is tested against 3 and 4 before the fade stubs are called.
   What setting did it represent in the Mac or other builds (screen depth, a "fade style" option)? With the value
   fixed at 4 the fade branch always runs, but the stubs do nothing.
2. Exact on-disk layout of `MIDIMAP.CFG`: is the u16 at offset 6 really "current setup index", with 0x36-byte setup
   records at 0x12 whose name is the first 16 bytes? Only the offsets are observed. On systems without the file
   (e.g. Windows 95 and later, where the MIDI mapper uses the registry) `Midi_Init` returns 0, but tracks may still
   open and play because `Midi_PlayTrack` ignores `g_midiOk` (§10.1, C18). Whether music is heard then needs a
   run (`GAPS.md` M2/E17).
3. Meaning of MenuDef fields +4 (0x3f/0x4e/0x42), +0x10 and +0x12 (0x84,0x46 / 0x81,0x88 / 0x8f,0x01). They might
   be Mac-era title widths, menu ids or enable flags. They are unused by 1078.
4. The 16-colour device table `DGROUP:0838` (`0,4,2,6,1,5,1,8,7,12,10,14,9,13,11,15`) looks like the Windows
   VGA-driver physical colour order, with red in bit 0 [I]. Logical 6 (brown) → 1 and the 7/8 swap should be
