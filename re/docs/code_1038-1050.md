# TMTWINCD.EXE code segments 1038, 1040, 1048, 1050

Resource manager, file I/O wrappers, palette manager and the 386 blitter library.

Sources: `re/win/ghidra_export/` (functions/*.c, disassembly.asm, functions.tsv), raw NE bytes of
`extracted/wincd/TMTWINCD/TMTWINCD.EXE` (segment table, relocation records, DGROUP at file 0x23c00),
and resources under `extracted/res/`. Scratch scripts: `extracted/scratch/code_1038/`
(`neseg.py`: NE segment dump, `relall.py`: relocation scan, `rund.py`/`render.py`: a RUND decoder
written from the 1050:03e7 description below, checked against TMT256 PMAPs 1000/1001/1251/2000/2448).

Each claim is tagged **[O]** (observed in code, bytes or decoded output) or **[I]** (inferred).
Addresses are `selector:offset` (Ghidra mapping, see CONTEXT.md). `DS:xxxx` and `11b8:xxxx` both
mean DGROUP offset xxxx (file offset 0x23c00 + xxxx). Everything is little-endian. "far" means a
16:16 pointer, stored as offset word then selector word.

## 2. Segment 1038: resource manager

The game was ported from the Mac and calls resources by integer id only. This module emulates
`GetResource`/`SizeResource` over the Win16 resource DLLs.

### 2.1 Type and DLL selection

**Type from id**: `Res_TypeForId` (1038:038a) **[O]**, signed 16-bit compares:

| id range | type string (DGROUP) |
|---|---|
| id < 900 | "BNDL" (0x741) |
| 900 ≤ id < 950 | "RRGB" (0x746) |
| 950 ≤ id < 1000 | "FFNT" (0x74B) |
| 1000 ≤ id < 4000 | "PMAP" (0x750) |
| 4000 ≤ id < 10000 | "SSND" (0x755) |
| id ≥ 10000 | "OTHR" (0x75A) |

This agrees with what the DLLs contain **[O]**: TMT.DLL BNDL 300..415, RRGB 900, FFNT 999,
OTHR 10550..20308; TMT16/TMT256 PMAP 1000..2448; sound DLLs SSND 4000..7552.

**Module handle from (type, id)**, used identically by 1038:00c9, 1038:03da and 1038:0ba8 **[O]**.
Only the **first character** of the type string is tested:

| condition | HINSTANCE global | DLL (loaded in 1018:0563) |
|---|---|---|
| type[0]=='P' | DS:0872 `g_hGfxLib` | TMT256.DLL on palette devices, TMT16.DLL otherwise |
| 'S' and 7000 ≤ id ≤ 7099 | DS:09DE | TM0SOUND.DLL (contains 7000..7041) |
| 'S' and 7100 ≤ id ≤ 7999 | DS:09E0 | TM1SOUND.DLL (7100..7552) |
| 'S' and 4000 ≤ id ≤ 4399 | DS:09E2 | TM2SOUND.DLL |
| 'S' and 4400 ≤ id ≤ 4799 | DS:09E4 | TM3SOUND.DLL |
| 'S' and 4800 ≤ id ≤ 5199 | DS:09E6 | TM4SOUND.DLL |
| 'S' and 5200 ≤ id ≤ 5599 | DS:09E8 | TM5SOUND.DLL |
| 'S' and 5600 ≤ id ≤ 5999 | DS:09EA | TM6SOUND.DLL |
| 'S' and 6000 ≤ id ≤ 6399 | DS:09EC | TM7SOUND.DLL |
| 'S' and 6400 ≤ id ≤ 6799 | DS:09EE | TM8SOUND.DLL (6400..6615) |
| 'S' and any other id | none: no FindResource call. `Res_GetSize` returns 0 (its local is pre-set to 0). In `Res_LoadCopy`/`Res_LockInPlace` the resource pointer and handle locals are **never written**, so the following NULL test reads stack garbage (undefined behaviour, not a guaranteed NULL). Shipped data never takes this path. | |
| anything else (BNDL/RRGB/FFNT/OTHR) | DS:09F0 `g_hTmtLib` | TMT.DLL |

(In 03da and 00c9 the id compares are signed (`JL/JGE`); in 0ba8 they are unsigned (`JC/JNC`).
This only matters for ids ≥ 32768, which are not used.)

**How a string type finds an integer resource [O]/[I]**: the code calls
`FindResource(hInst, MAKEINTRESOURCE(id), "PMAP")`, i.e. the type is passed as a **string**. The
DLLs' NE resource tables only have integer types (0xFF01.. = 32513..). Each DLL also has a type 15
resource. Its 12-byte records `{u16 cb=12; u16 typeOrdinal (0xFF01..); u16 idOrdinal; "TYPE\0"; "\0"}`
(observed in TMT.DLL/15/1) are the Windows 3.0 `RT_NAMETABLE` format, which KERNEL uses to turn
string type/name lookups into ordinals **[I]**. A re-implementation can do the same: map
(4-char type, id) to the NE resource whose type ordinal comes from that DLL's type-15 table.

**Sizes [O]**: `SizeofResource` returns the NE-aligned length (multiple of 512 bytes for these DLLs,
alignment shift 9). Every size this module computes, copies or stores is that rounded length,
not the payload length.

### 2.2 In-memory formats

**Plain resource copy [O]**: a `NewPtr` block holding a byte copy of the resource, length
`Res_GetSize(type,id)`.

**BNDL on disk [O]** (TMT.DLL type 32513):

| offset | size | field |
|---|---|---|
| 0 | 4 | magic "BNDL" |
| 4 | 4 | u32 count (the code reads only the low u16 at +4) |
| 8 | 4·count | u32 member resource ids (low u16 = id, high u16 = 0) |

Example: BNDL 300 has count 0x45 (69) and lists PMAP ids 0x4E3 (1251).. (frames of a walking
character); BNDL 301 has 10 PMAPs from 0x514.

**BNDL after `GetResource` expansion [O]** (1038:076f). The buffer is allocated at **twice** the
rounded resource size (1038:00c9 doubles it for type "BNDL"), so there is room for a second table:

| offset | size | field |
|---|---|---|
| 0 | 4 | "BNDL" |
| 4 | 2 | count n (u16) |
| 6 | 2 | (high word of the original count, untouched) |
| 8 + 4i, i<n | 4 | **far pointer** to the loaded member i (itself expanded if it is a BNDL) |
| 8 + 4(n+i), i<n | 4 | u32 size of member i = `Res_GetSize(TypeForId(id_i), id_i)` (rounded; doubled for BNDL members) |

Accessors: `Bndl_GetCount` (1038:0088) = u16 at +4; `Bndl_GetEntry(b,i)` (1038:0061) = u32 at
`b + (i+2)*4`; `Bndl_SetEntry(b,i,v)` (1038:00a1) stores it. Code that walks animation frames uses
`Bndl_GetEntry(b, i)` for i < count to get the far pointer of frame i (e.g. 1198:0000 on BNDL 300,
1168:00ba on 0x141/0x146, 1178:0041, 1190:009b). **[O]** No live caller reads the size half: every
non-1038 call site of 1038:0061 passes an index below `count` (constants, `i`, `i+1`, `3i..3i+2`,
or a stored frame number). `Bndl_GetEntry(b, count+i)` occurs only in the dead `Flat_Unflatten*`
routines 1038:09e4 / 1038:0ad2. A port may therefore omit the size table. Because
`8 + 8n ≤ 2·roundup512(8 + 4n)` always holds, the doubled buffer is always large enough. The upper
half is uninitialised memory until filled (NewPtr does not zero).

**Flat format [O]** (1038:08eb, recognised by 1030:0082):

| offset | size | field |
|---|---|---|
| 0 | 1 | 'F' (0x46) |
| 1 | 1 | 0 |
| 2 | 4 | u32 payload size |
| 6 | size | payload = what `GetResourceInto` produced (may be an expanded BNDL) |

Only dead code builds or consumes this format (see §2.6). DisposePtrDeep still handles it.

**Scratch buffer [O]**: `g_resScratch` (DS:3D8C, far) points to a 280 000-byte (0x445C0)
`NewPtr` block allocated by `Res_AllocScratch` (called once from init 1018:07f3). 24 call sites
(segments 10f0..1198) load resources into it with `Res_LoadToScratch(id)` and then read
`g_resScratch` directly. `Res_LockInPlace` temporarily makes `g_resScratch` point at a locked
resource instead (§2.4.6).

### 2.4 Algorithms

#### 2.4.1 `Res_GetSize(type, id)`: 1038:00c9 [O]
```
h   = module_for(type, id)            // table in 2.1; for an unmapped SSND id return 0
sz  = SizeofResource(h, FindResource(h, MAKEINTRESOURCE(id), type))   // u32, rounded
if memcmp("BNDL", type, 4) == 0: sz *= 2
return sz
```
There is no NULL check on FindResource.

#### 2.4.2 `Res_LoadCopy(type, id)`: 1038:03da [O]
```
size = Res_GetSize(type, id)                       // doubled for BNDL
h    = module_for(type, id)
hRes = LoadResource(h, FindResource(h, MAKEINTRESOURCE(id), type))
src  = LockResource(hRes)
if type[0]=='P' && g_paletteDevice: PixMap_RemapToSystem(src)   // in place, before the NULL test
if src == NULL:
    MessageBox(NULL, DS:075F, DS:0776, MB_ICONHAND|MB_SYSTEMMODAL /*0x1010*/); return NULL
dst  = NewPtr(size)
BlockMove(src, dst, type=="BNDL" ? size/2 : size)  // i.e. always the rounded resource size
GlobalUnlock(hRes); FreeResource(hRes)
g_inResourceLoad = 1; Input_Flush(); g_inResourceLoad = 0
return dst
```
Notes: (a) In 256-colour mode the PMAP pixels are translated to physical palette indices **while
still in the resource segment**, then copied. FreeResource follows right away, so a later load starts
again from the original file bytes **[O]**/**[I]**. (b) 16-colour PMAPs are copied unchanged.
(c) Only one direct far caller: 1068:0000 (font loader), which passes type "FFNT" (DS:09A8).
(d) For an 'S' id outside every sound range, `hRes` (DI) and `src` ([bp-4]) are never assigned
(1038:0661..066b jump straight to the test at 1038:06d3), so the result is undefined (§2.1).

#### 2.4.3 `Res_GetResourceTree(id)` (= `GetResource`): 1038:076f, wrapper 1038:08c5 [O]
```
p = Res_LoadCopy(Res_TypeForId(id), id)
if memcmp(p, "BNDL", 4) == 0:                 // no NULL check on p
    n = Bndl_GetCount(p)
    for i in 0..n-1:
        sub = low u16 of entry[i]
        entry[n+i] = Res_GetSize(Res_TypeForId(sub), sub)
        entry[i]   = Res_GetResourceTree(sub)  // recursion: nested bundles expand fully
return p
```
The result is a tree of NewPtr blocks. It is freed with `DisposePtrDeep` (1030:0082). Each member
is loaded separately, so the message pump runs once per member.

#### 2.4.4 `GetResourceInto(id, dst)`: 1038:082d, wrapper 1038:08d4 [O]
```
size = Res_GetSize(Res_TypeForId(id), id)
tmp  = Res_GetResourceTree(id)
BlockMove(tmp, dst, size)        // full rounded (and for BNDL doubled) size
DisposePtr(tmp)                  // shallow: children of a BNDL stay allocated, now owned via dst
return size
```
The caller must supply `size` bytes. Only far caller: 1118:000b loads **RRGB 900** (1024 bytes on
disk: 768 RGB bytes + padding) into DS:3D90..418F, then calls `Pal_SetFromRGB(DS:3D90)` (§4).

#### 2.4.5 Scratch loads [O]
* `Res_AllocScratch` 1038:0022: `g_resScratch = NewPtr(280000)`.
* `Res_FreeScratch` 1038:0038: `if (g_resScratch && !g_resLockedHandle) { DisposePtrDeep(g_resScratch); g_resScratch = 0; }`. The zeroing (1038:0057) is **inside** the condition: both early-outs (1038:003e, 1038:0045) jump straight to the RETF. So while a resource is locked in place, `g_resScratch` keeps pointing at the locked resource. The deep dispose means a BNDL that was loaded into scratch has its members freed here too. Called by 1010:00be (shutdown) and 1038:0ba8.
* `Res_LoadToScratch(id)` 1038:088a: `size = GetResourceInto(id, g_resScratch); if size > g_resScratchMax: g_resScratchMax = size; return size`. There is **no bounds check** against 280000. In practice it is never exceeded **[O]**: every id passed is listed in the table below, and the largest resource of any of these types in any DLL is 101 376 bytes (TMT256 PMAP 1041, NE-rounded; TMT16 maximum 93 696, OTHR maximum 19 456). Sounds, which can be up to 232 960 bytes (TM1SOUND 7133), never go through scratch copies; they use `Res_LockInPlace`.
* Quirk **[O]**: `Res_LoadToScratch` does not free what was in scratch before. If scratch held an expanded BNDL (only BNDL 327 is ever loaded this way, by 1130:0068), its 33 member blocks leak as soon as another resource overwrites the header. They are freed only if the BNDL header is still in scratch when `Res_FreeScratch` runs (e.g. from `Res_LockInPlace`). A port should give scratch loads proper ownership.

#### 2.4.6 Lock-in-place: `Res_LockInPlace(id)` 1038:0ba8 and `Res_UnlockInPlace()` 1038:0ef8 [O]
Used for **speech/sound playback**: both callers, 1088:01a9 (`Wave_PlayResUntilEvent`, see
code_1058-1090.md) and 1138:0283 (title/intro narration wait, see code_10f8-1148.md), pass an SSND id,
then hand `g_resScratch` (the locked SSND bytes) to `Wave_Play` 1088:0014 and call
Res_UnlockInPlace when playback ends **[O]** (1088:01a9 lines 12-13/37, 1138:0283 lines 15-16/30 of
the decompiled files; Ghidra drops the pushed id from the call). Locking avoids copying sounds of up to
~230 KB. Because the ids are SSND, the BNDL size doubling never applies here.
```
Res_LockInPlace(id):                 // id treated as unsigned
    Res_FreeScratch()
    type = Res_TypeForId(id); size = Res_GetSize(type, id)
    hRes = LoadResource(module_for(type,id), FindResource(...)); p = LockResource(hRes)
    if type[0]=='P' && g_paletteDevice: PixMap_RemapToSystem(p)
    if p == NULL: MessageBox(NULL, DS:07A3, DS:07BA, 0x1010); return 0
    g_inResourceLoad = 1; Input_Flush(); g_inResourceLoad = 0
    g_resLockedHandle = hRes; g_resScratch = p
    return size                      // doubled for BNDL, but no BNDL expansion is done here
Res_UnlockInPlace():
    if g_resLockedHandle: GlobalUnlock(h); FreeResource(h); g_resLockedHandle = 0
    Res_AllocScratch()               // fresh 280000-byte scratch block
```
Re-implementation: a read-only view of the resource bytes. While locked, `g_resScratch` must not be
written. A locked PMAP has already been remapped to physical colours. If `Res_LockInPlace` were
called again before `Res_UnlockInPlace`, `Res_FreeScratch` would do nothing and the old handle would
be overwritten (leaked). Both callers always unlock first.

#### 2.4.7 Dead code [O] (no far relocation and no near call references them; scanned with `relall.py`)
* 1038:0000 (34 bytes, Ghidra made no function): `if (g_resCachedTree) { DisposePtrDeep(g_resCachedTree); g_resCachedTree = 0; }`.
* 1038:0956 `Res_LoadFlatCopy(id)`: `n = Res_LoadFlatToScratch(id); q = NewPtr(n); BlockMove(g_resScratch, q, n); return q`.
* 1038:09a9 `Res_LoadFlatInto(id, dst)`: same, but into `dst`.
* 1038:09e4 `Flat_Unflatten(flat)`: `size = *(u32*)(flat+2); p = NewPtr(size); BlockMove(flat+6, p, size); if p is BNDL: for i<n: s = entry[n+i]; q = NewPtr(s); BlockMove(entry[i], q, s); entry[i] = q;` return p. This duplicates the members one level deep (no recursion). `Flat_GetSize` (1038:093a) is used only here.
* 1038:0ad2 `Flat_UnflattenInto(flat, dst)`: the same as 09e4 with `dst` instead of `p`.

### 2.5 Re-implementation summary for 1038
* `GetResource(id)`: decide the type by id range, read the resource from the right DLL, and return a
  byte buffer. For BNDL, return an object holding `count` child objects plus each child's rounded
  size. Children are loaded recursively, and a missing child is fatal in the original.
* `GetResourceInto(id, dst)` copies the rounded length. Callers' buffers are sized for that
  (e.g. palette 900 → 1024 bytes).
* In 256-colour mode PMAP bytes are converted logical→physical on load (§4.4). A modern engine
  that controls the palette can make the mapping the identity map, or use RGB equality (§4.5).
* After each load the original pumps the Windows message queue and blocks command dispatch
  (`g_inResourceLoad`). A port may simply keep its event loop alive during loads.

### 4.2 Initialisation and the game palette

`Pal_Init` (1048:02b2, called from init 1018:0563) **[O]**:
```
if g_paletteDevice:
    if g_hPalette: DeleteObject(g_hPalette)
    g_hPalette = Pal_CreateBlack()                    // 256 entries all {0,0,0,0}
    SelectPalette(g_hdcScreen, g_hPalette, FALSE)
    if !g_useWinG: SelectPalette(g_hdcMem, g_hPalette, FALSE)
else:
    g_transparentIndex = 3
```
`Pal_CreateBlack` (1048:0000): LocalAlloc(LMEM_ZEROINIT, 0x408) LOGPALETTE, `palVersion=0x300`,
`palNumEntries=256`, CreatePalette, LocalFree. `Pal_CreateSystemCopy` (1048:0034): same, but the
entries are filled by `GetSystemPaletteEntries(GetDC(NULL), 0, 256)` (DC released). It is a
throw-away palette used only as a "nearest colour in the system palette" oracle. Every user calls
`DeleteObject` on it straight after.

`Pal_SetFromRGB(rgb)` (1048:010a) **[O]**. It is called once, from the game start routine
1118:0000, with palette resource **RRGB 900** copied to DS:3D90:
```
if !g_paletteFirstLoad: return
g_paletteFirstLoad = 0
if !g_paletteDevice: return
lp = LOGPALETTE(256); for i<256: lp[i] = {rgb[3i], rgb[3i+1], rgb[3i+2], flags 0}
SetPaletteEntries(g_hPalette, 0, 256, lp); RealizePalette(g_hdcScreen)
if g_useWinG: 1008:02ec()          // WinG identity palette + WinGSetDIBColorTable (other module)
sys = Pal_CreateSystemCopy()
for i<256: g_logToPhys[i] = GetNearestPaletteIndex(sys, PALETTERGB(lp[i].r, lp[i].g, lp[i].b))
DeleteObject(sys)
Pal_ResetTransparentKey()
LocalFree(lp)

```
Because of the one-shot flag, **the palette is set once per run and never changed** **[O]**
(`Pal_LoadById` 1048:0247 would allow a change but nothing calls it). No palette animation or fades
happen here.

`Pal_LoadById(id)` (1048:0247, dead) **[O]**: if `id != g_curPaletteId && g_paletteDevice`, it sets
`g_curPaletteId = id`, Find/Load/Locks resource ("RRGB", id) in TMT.DLL, calls
`Pal_SetFromRGB(ptr)` (a no-op after the first call), then unlocks and frees.

### 4.3 Colour key and fore colour

* `Pal_ResetTransparentKey` (1048:008b) **[O]**: 256-colour:
  `g_transparentIndex = GetNearestPaletteIndex(systemCopy, PALETTERGB(0,0,170))` (COLORREF
  0x02AA0000). 16-colour: `g_transparentIndex = 3`. **[O]** In palette 900, logical indices 15 and
  241 are (0,0,170), and sprite backgrounds use that blue (TMT256 PMAP 1251 decoded). TMT16 sprites

* `Pal_SetTransparentKeyRGB(r,g,b)` (1048:00b7): key = nearest system index to RGB(r,g,b). In

* `Pal_SetForeColor(n)` (1048:02fd, 59 call sites) **[O]**: 256-colour:

* `Pal_SetForeColorRGB(r,g,b)` (1048:036f, dead): 256-colour only, `g_foreColorPhys = nearest(r,g,b)`.
* `Pal_GetForeColor()` (1048:03bb) returns `g_foreColorIndex` (called from 1058 and 10c0).
* 1058:07d0 (fill rect) and 1058:09b8 (frame rect) use the same two tables. In 16-colour mode they

### 4.4 Remap table translation

`Pal_TranslateRemapTable(t)` (1048:03bf) **[O]**. `t` is a table indexed by logical colour that
yields logical colours. It is rewritten so that it is indexed by physical colour and yields
physical colours:
```
u8 tmp[256]
for i<256: tmp[g_logToPhys[i]] = g_logToPhys[t[i]]
copy tmp -> t (256 bytes)
```
Physical slots that no logical index maps to keep stack garbage **[O]** (uninitialised local). They
are never looked up, because framebuffer pixels are always mapped values.

### 4.5 Re-implementation notes
* The game always runs with palette 900. If the engine composes in 8-bit logical indices,
  "physical index" equality has to be emulated. 900 has duplicate colours (154 distinct RGBs;
  e.g. 0 and 77 are both white, 15 and 241 are both (0,0,170)), and `GetNearestPaletteIndex` folds
  duplicates onto one physical slot. Suggested: `canon[i] = min{ j : rgb[j] == rgb[i] }`; key test
  `canon[pix] == canon[15]`; apply remap tables on canonical indices **[I]**. Composing in RGB
  avoids the issue entirely.
* 16-colour mode: key nibble 3, colours via `g_vga16Index`, no palette work at all.

## 5. Segment 1050: blitter library (hand-written 386 assembly)

### 5.1 Surfaces and formats

**Framebuffer [O]** (allocated by 1018:0563 / 1058:1493 / 1058:153b; selector in DS:429E
`g_frameSel`): one large block reached with 32-bit offsets through a single selector (Win 3.1
enhanced mode gives the first selector of a huge block a limit covering the whole block **[I]**).
The buffer is 512 pixels wide. 1018 creates it with height 0x41F (1055) rows, more than the 384
visible rows (rows beyond 384 are presumably off-screen storage **[I]**). Layout:

| mode (`g_paletteDevice`) | pixel format | stride | address of (x, y) |
|---|---|---|---|
| 256-colour (nonzero) | 8bpp, physical palette index | 0x200 bytes | `y*512 + x` |
| 16-colour (zero) | 4bpp packed, **high nibble = even (left) pixel** | 0x100 bytes | byte `y*256 + x/2`; high nibble if x even, low nibble if x odd |

In 256-colour mode the framebuffer *is* the bit storage of the DDB selected into `g_hdcMem` (bits
selector taken from the GDI object, 1058:1525). In 16-colour mode the 4bpp buffer is a separate
GlobalAlloc block. `Blit4_ToPlanar` converts it into the 4-plane DDB bits (selector DS:429C
`g_planarSel`), and 1058:05bc then BitBlts (SRCCOPY) `g_hdcMem` to the screen at offset
(DS:086E, DS:0870). This applies when WinG is not used **[O]**.

**Planar DDB layout [O]** (from 1050:09e7): per scanline 256 bytes = 4 planes × 64 bytes
(512 px / 8). Plane k (offset k·0x40 within the scanline) holds bit k of each pixel, MSB = leftmost
pixel of the 8-pixel group.

**PIXMAP in memory [O]**:
```
struct PIXMAP { u16 width; u16 height; u8 pixels[]; }
  4bpp (TMT16):  rows of (width+1)/2 bytes, high nibble first, no other padding
  8bpp (TMT256): rows of width bytes
  8bpp RUND:     bytes 4..7 = "RUND", RLE stream from byte 8 (format in 5.3.6)
```
(e.g. TMT16 1251 = 63×109, 32×109 = 3488 data bytes; TMT256 1000 = 512×364 RUND.)

**Calling convention [O]**: far cdecl, `ENTER 0,0`. Arguments start at [bp+6], every scalar is a
word unless stated, far pointers are offset then selector, dword arguments take 4 bytes. DS, ESI and
EDI are preserved. ES/DS are loaded from `g_frameSel` (DS:429E) or from the far pointer arguments.
Only the 0x67-prefixed string instructions use 32-bit ESI/EDI/ECX. Several routines contain
16-bit-only instructions (noted as quirks below).

### 5.2 Routines

Notation: `FB4(x,y)` is a nibble of the 4bpp framebuffer; `FB8(x,y)` is a byte of the 8bpp one.
`key4 = g_transparentIndex & 0x0F`, `key8 = g_transparentIndex`.

#### 5.2.1 Opaque whole-pixmap draws (callers: 1058:0c78 `PixMap_DrawOpaque`)
* **`Blit4_DrawPixmap(x, y, pm)` 1050:0029**: for each of `pm.height` rows, copy `pm.width`
  nibbles to `FB4(x.., y+row)`. Source bytes are consumed sequentially, ceil(w/2) per row. Even x:
  `w/2` whole bytes, then if w is odd the last source high nibble goes to the destination high
  nibble. Odd x: each source byte is split (first pixel into the low nibble of the current byte,
  second pixel into the high nibble of the next byte). **No clipping.**
* **`Blit8_DrawPixmap(x, y, pm)` 1050:00c9**: copies `pm.height` rows of `pm.width` bytes to
  `FB8(x, y+row)`. No clipping.
* 1058:0c78 picks the routine: 16-colour → 0029. 256-colour → `Blit8_DrawRund(x, y, w, h, -1, pm)`
  if the pixmap is RUND, else 00c9.

#### 5.2.2 Keyed sub-rectangle draws (callers: 1058:0d43 normal, 1058:114c mirrored)
The callers clip against the inclusive clip rectangle DS:0868 (left), DS:0864 (top), DS:086A
(right), DS:0866 (bottom) **[O]**. They then call:

* **`Blit4_DrawPixmapKeyed(dx, dy, w, h, pm, u32 sx, u32 sy)` 1050:0120**: source row stride
  `rb = (pm.width+1)/2`, source start byte `pm+4 + sy*rb + sx/2`. For each of `h` rows and `w`
  pixels: `p = src nibble (sx+i, sy+row)`, and `if p != key4: FB4(dx+i, dy+row) = p`. Four unrolled
  cases by parity `(sx&1, dx&1)`, all equivalent to the loop above.
* **`Blit4_DrawPixmapKeyedMirror(dx, dy, w, h, pm, u32 sx, u32 sy)` 1050:04e4**: the same, except
  that source pixel `sx+i` goes to `FB4(dx+w-1-i, dy+row)`. The caller passes
  `sx = x + pm.width - clipRight` (exclusive right) so that the mirror image of the full sprite is
  clipped correctly.
* **`Blit8_DrawPixmapKeyed(dx, dy, w, h, pm, u16 srcSkip, u32 srcOfs)` 1050:02e3**: source pointer
  `pm+4+srcOfs`. Per row: for i<w, `p = *src++`, `if p != key8: FB8(dx+i, dy+row) = p`. After each
  row, `src += srcSkip`. Caller: `srcOfs = (clipTop-y)*pm.width + (clipLeft-x)`,
  `srcSkip = pm.width - w`.
* **`Blit8_DrawPixmapKeyedMirror(...)` 1050:06a7**: the same, but the destination runs from
  `FB8(dx+w-1, ..)` leftwards (STD/STOSB, CLD restored at the end). Caller:
  `srcOfs = (clipTop-y)*pm.width + (x + pm.width - clipRight)`.
* 1058:0d43 / 114c / 0f7e first decode RUND pixmaps into a temporary NewPtr (1058:0400). There is
  one exception: if a RUND sprite lies entirely inside the clip rectangle, 1058:0d43 calls
  `Blit8_DrawRund(x, y, w, h, key8, pm)` directly. While drawing, these callers temporarily
  increment DS:086A and DS:0866 by 1 and restore them afterwards.

#### 5.2.3 Mask remap ("shadow/tint") draw
* **`Blit8_DrawMaskRemap(dx, dy, w, h, pm, u16 srcSkip, u32 srcOfs, u8 far* table)` 1050:035f**
  **[O]**: same walk as 02e3, but for every source pixel `!= key8` it does
  `FB8(dx+i, dy+row) = table[FB8(dx+i, dy+row)]` (XLAT through FS:BX). **The source colour is only
  used as a mask.** Only caller: 1058:0f7e, with `table = DS:0876` (`g_shadowTable`). In
  16-colour mode 1058:0f7e falls back to the normal keyed blit 1050:0120, which draws the sprite in
  its own colours. **Dead at runtime [O]**: 1058:0f7e is reached only from 1058:1379, and 1058:1379
  has no far relocation (NE relocation scan over all segments, scratch `code_1038_v3/relall58.py`)
  and no near caller (functions.tsv). A port need not implement this routine.

#### 5.2.4 RUND decoder: `Blit8_DrawRund(x, y, w, h, key, pm)` 1050:03e7 [O]
Decodes the RLE stream at `pm+8` straight into `FB8(x.., y..)`, `w` pixels per row, `h` rows. No
clipping. `key` is a word: `0xFFFF` = opaque, otherwise pixels equal to `(u8)key` are skipped
(destination left unchanged).
```
stream: repeat { c = next byte
                 if c & 0x80: run     count = c & 0x7F, value = next byte  -> count copies of value
                 else:        literal count = c, then count raw bytes }
```
Rows are filled left to right. **Packets may span row boundaries.** If a packet's count is larger
than the pixels left in the row, the rest is carried into the next row (EBP holds the remaining
count, bit 31 = "carry is a run"). A carried run re-reads its value byte (the decoder steps ESI back
by one), and a carried literal continues with the following raw bytes. In other words, the stream
is a single RLE of the `w·h` pixel sequence in row-major order. Zero counts: a **run** of count 0
(`0x80 v`) is a well-defined no-op that consumes 2 bytes (`REP STOSB` with ECX=0). A **literal** of
count 0 is unsafe: the loop body (LODSB/STOSB, then `LOOP` on CX) runs 65536 times. The shipped
data contains no zero-count packet of either kind (checked over all 760 RUND PMAPs). Treat both as
no-ops. Verified by `rund.py`: PMAP 1000 (512×364) consumes 62619 of its 62976 bytes (the rest is
zero padding). PMAPs 1001/1251/2000/2448 behave the same way, and the decoded images are correct
(scratch PNGs `pmap_1000.png`, `pmap_1251.png`). See the verification section for the full-corpus
check (TMT256 1380..1383 are the only non-RUND 8bpp PMAPs).

#### 5.2.5 Framebuffer rectangle operations
* **`Blit4_FillRect(x, y, w, h, color)` 1050:097c**: `FB4(x+i, y+j) = color & 0xF`.
* **`Blit4_CopyRect(sx, sy, w, h, dx, dy)` 1050:0732 / `Blit8_CopyRect` 1050:0899**:
  framebuffer → framebuffer opaque copy, rows top-down, pixels left-to-right (no overlap handling;
  wrong if the destination overlaps below/right of the source **[I]**). 0732 handles the 4 nibble
  parity cases of `(sx&1, dx&1)`. Caller 1058:0b6a first calls 1058:068e(dx, dy, w, h) (probably a
  dirty-rectangle add **[I]**).
* **`Blit4_CaptureRect(x, y, w, h, dst)` 1050:0c0b / `Blit8_CaptureRect` 1050:0c6e**: write
  `dst.width=w, dst.height=h`, then copy rows starting at the framebuffer byte of (x, y). 4bpp
  copies exactly `w/2` bytes per row (as words plus a final byte if `w/2` is odd). 8bpp copies
  `2*(w/2)` bytes (as dwords plus a final word). Both assume even `w`, and 4bpp also even `x`. The
  caller 1058:1643 enforces this (odd x → x-1, w+1; odd w → w+1). The captured pixmap has the
  normal PIXMAP layout.
* **`Blit4_RemapRect(x, y, w, h, table)` 1050:0cfa / `Blit8_RemapRect` 1050:0db5**: in place
  `pixel = table[pixel]` (4bpp: `table[nibble] & 0xF`). Callers: 1058:1825 (table built by 1058:16b5
  from a `{u8 n; n × {u8 to, u8 from}}` substitution list over an identity table; **dead**, reached
  only from the unreferenced 1058:187f) and 1058:19b2 `Gfx_HighlightRect` (the only live caller,
  used by 1150:0d2d for the reading highlight). 19b2 builds the table from `g_egaRGB`/`g_vga16Index`
  **[O]**: every colour → EGA 14 (yellow); then EGA 0 (black) → EGA 1 (dark blue), EGA 4 (dark red) →
  EGA 6 (brown), EGA 14 → EGA 1. In 256-colour mode each EGA colour is looked up as the nearest
  system-palette index. In 16-colour mode `g_vga16Index[n]` is used. 4bpp quirks **[O]**:
  - when x is odd, the "leading pixel" step remaps the **high** nibble of byte `y*256+x/2`, which is
    pixel x-1, and does not advance;
  - the main loop then processes `floor(w'/2)` whole bytes starting at that same byte, where
    `w' = w` (x even) or `w-1` (x odd);
  - if `w'` is odd, the trailing step remaps the **low** nibble of the next byte;
  - the main loop counter is CX, so `floor(w'/2) == 0` loops 65536 times.

  Correct only for even x and even w ≥ 2. A re-implementation should simply remap the exact
  rectangle. 0db5 has no such issues.

#### 5.2.6 Present helper: `Blit4_ToPlanar(x, y, w, h)` 1050:09e7 [O]
The span is widened to whole 8-pixel groups: `x0 = x & ~7`,
`groups = ((x+w-1)>>3) - (x>>3) + 1`. For each row and group, it reads 4 chunky bytes (8 pixels
p0..p7, p0 = high nibble of the first byte) from `g_frameSel:y*256 + x0/2`. For each plane k=0..3
it writes `byte = Σ bit_k(p_j) << (7-j)` to `g_planarSel:y*256 + x0/8 + k*0x40`. This is done with
the mask/add trick `((d << (3-k)) & 0x88888888) + 0x38383838 & 0xC0C0C0C0`, then folding the 4
bytes into one. Called by 1058:05bc (present) for 16-colour, non-WinG mode, before
`BitBlt(screen, DS:086E+x, DS:0870+y, w, h, g_hdcMem, x, y, SRCCOPY)`. The present rectangle is
clipped to 0..512 × 0..384 first.

#### 5.2.7 Pixmap utilities
* **`Pix8_RemapToPhysical(pm)` 1050:0b36**: in place, for all `w*h` bytes:
  `b = g_logToPhys[b]` (XLAT on DS:4193). It is reached from `Res_LoadCopy`/`Res_LockInPlace`
  through 1058:1d28 for uncompressed 256-colour PMAPs.
* **`Pix4_ReplaceColor(pm, from, to)` 1050:0b6f**: every nibble `== from` becomes `to`, over
  `ceil(w/2)*h` bytes. **`Pix8_ReplaceColor(pm, from, to)` 1050:0bc9**: every byte `== from`
  becomes `to`, over `w*h` bytes (it loads BX=0x4193 but never uses it). Caller 1058:13be picks by
  mode. For RUND pixmaps it decodes to a temporary first. **Dead [O]**: 1058:13be has no far
  relocation and no near caller.
* **`Pix4_CopyData(src, dst)` 1050:08fb / `Pix8_CopyData` 1050:093b** (dead): copy the pixel bytes
  (`ceil(dst.w/2)*dst.h` resp. `dst.w*dst.h`, sizes taken from **dst**'s header) from `src+4` to
  `dst+4`.
* **`Mem_RemapBytes(buf, u32 n, table)` 1050:0ccf**: `buf[i] = table[buf[i]]`. Only the low 16
  bits of n are used (LOOP on CX, STOSB on DI): n must be 1..65535, and 0 means 65536. Caller
  1058:1712, which is reached only from the unreferenced 1058:174b, so this routine is **dead [O]**.
* **`BlockMove(src, dst, u32 n)` 1050:0e10**: forward byte copy with 32-bit ECX, offsets
  zero-extended. It does not handle overlap. It is the Mac `BlockMove` emulation used by 1038.
* **`Cpu_Is386()` 1050:0000** (41 bytes, not a Ghidra function, unreferenced): tries to set
  EFLAGS.AC (bit 18) with `OR EAX,0x40000` / POPFD and reads it back. It returns 1 if the bit cannot be set (80386) and 0 on 486 or later. EFLAGS is restored.

### 5.3 Quirks summary (all **[O]**)
1. 1050:0120, case "src x odd, dst x even" (offset 0x0299/0x02b0): the source is read with
   16-bit `LODSB` (DS:SI, no 0x67 prefix), so the source offset wraps at 64 KB. This only matters
   for 4bpp sprites whose row offset exceeds 0xFFFF. The other three cases and 04e4 use ESI.
2. 1050:0cfa edge handling (5.2.5). 1050:0ccf is a 16-bit count. A zero-count RUND literal is
   unsafe.
3. No routine clips. Clipping is done in 1058 (only 5.2.2 callers clip). 5.2.1 and
   `Blit8_DrawRund` with key -1 assume the pixmap fits.
4. Copy routines are forward-only (no memmove semantics).
5. Reading aid: Ghidra's listing prints the bytes `67 26 67 8A 07` / `67 26 67 80 27 xx` (1050:0cea,
   0d42, 0d50, 0d65, 0d8b, 0df1) as `ES:[BX]`. With the 0x67 prefix, ModRM r/m=111 means
   **`ES:[EDI]`** (the framebuffer or buffer pixel). BX is only the XLAT table pointer.

## 7. Open questions

1. **16-colour pixel values**: what physical colours do nibble values 0..15 have on the target
   16-colour DDB? `g_vga16Index` (EGA 6→1, 7→8, 8→7) suggests a driver-specific order. The
   standard Windows *DIB/logical* 16-colour order puts light grey (C0C0C0) at 7 and dark grey at 8.
   A 16-colour port needs the right palette for TMT16 PMAP nibbles (key nibble 3).
   *Adversarial-pass evidence* **[O] statistics / [I] conclusion**: for each nibble value, I averaged
   the palette-900 RGB of the TMT256 pixel at the same position over 7 pixmaps
   (1000/1006/1017/1036/1251/2210/1380, scratch `code_1038_verify/pal16.py`). The result matches
   the VGA *device* order 0 black, 1 dark red, 2 dark green, 3 dark yellow, 4 dark blue, 5 dark
   magenta, 6 dark cyan, **7 = 808080, 8 = C0C0C0**, 9 red, 10 green, 11 yellow, 12 blue,
   13 magenta, 14 cyan, 15 white. For example, nibble 7 averages (126,127,120), nibble 8
   (180,185,185), nibble 1 (114,83,62) (tree trunks) and nibble 3 (0,0,170) (the key colour). This
   agrees with every entry of `g_vga16Index`. With the EGA bit order, tree trunks render blue.
   What remains open is only the exact intensities the driver uses (128 vs 170 for the dark colours).
