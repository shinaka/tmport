# TMTWINCD.EXE code segments 10f8, 1100, 1108, 1110, 1118, 1120, 1128, 1130, 1138, 1140, 1148

Game main loop, climb layout and clue generator, net shop, rescue coin pile, music manager,
New Player Messages (hints), title/story attract sequence, menu bar and menu commands, plus
three stub/dead modules.

Sources: `re/win/ghidra_export/` (functions/*.c, disassembly.asm, functions.tsv), raw NE bytes of
`extracted/wincd/TMTWINCD/TMTWINCD.EXE` (segment table, relocation records, DGROUP at file
0x23c00), and resources under `extracted/res/`. Code that Ghidra did not turn into functions
(1128:002d-00d5, 1140:0000-0014, 1140:0062-008b, 1140:00c2-00cb, all of 1148) was disassembled
with a headless Ghidra script on a private copy of the project. Scratch scripts are in
`extracted/scratch/code_10f8/`: `gaps.py` (finds code that is not in a function), `relocs.py`
(full NE relocation scan, resolves entry-table ordinals), `dg.py` (DGROUP hexdump), `pm16.py`
(renders TMT16 4bpp PMAPs, used only to identify pictures), `scripts/DisGaps.java`.

**Second pass (re-verification).** All 41 Ghidra functions plus the gap code were re-read against
`functions/*.c` and `disassembly.asm`; the DGROUP tables (word tables via their NE relocations,
hint-bit table, title voice tables, menu records, music variables), the BNDL contents (327, 328,
400, 401, 302) and every relocation that targets these segments were re-checked. Corrections and
additions from that pass: title voice tables re-based (§12.1), castle-climb hint triggers (§3.9),
`g_unk13cd` 11b8:13cd (§10.2), every caller of `MenuCmd_Exit` / `Game_ExitNow` (§13), and the
other-segment helper names synchronised with the other teams' names files (§1.1, §8). Scratch for
this pass is in `extracted/scratch/code_10f8_r2/` (`strs.py` resolves relocated far-pointer
string tables).

Each claim is tagged **[O]** (observed in code, bytes or decoded data) or **[I]** (inferred).
Addresses are `selector:offset` (Ghidra mapping, see CONTEXT.md). `11b8:xxxx` and `DS:xxxx` both
mean DGROUP offset xxxx (file offset 0x23c00 + xxxx). Everything is little-endian. "far" means a
16:16 pointer stored as offset word then selector word. Names of functions in other segments
come from the other teams' names files (`re/names/*.tsv`) where they exist.

vtables or `this` pointers: every function is a plain Borland C function using global data.
None of the functions in these segments is a Borland RTL routine. The RTL routines they call are
`F_SCOPY@` (1000:02f7, struct copy of CX bytes), `rand` (1000:0859), `srand` (1000:0842),
`setjmp` (1000:32e5) and `longjmp` (1000:3309).

have no frame: the menu handlers 1140:0000/0062/0098/00cc and helpers 1140:0008/008c, plus
1128:00d6/00dc/00ee/00ef/012f/0151, 1110:0000/0037/0059/00aa, 1138:0000/0037, 10f8:0241 and 1148:*. Near functions:
1100:0000 and 1100:06cc (called only from 1100:04b5), 1148:0001.

**[I]** Each segment is one Borland source module. The modules' initialised data sits in DGROUP
in segment order: 10f8 at 0x1064..0x106b, 1100 at 0x106c..0x1287, 1110 at 0x1288..0x128c,
1118 at 0x128e..0x1299, 1120 at 0x129a..0x13c4, 1128 at 0x13c6..0x13cd, 1130 at 0x13ce..0x141b,

## 2. Shared conventions

### 2.1 Offscreen layers and screen layout [O]

The offscreen buffer is 512 pixels wide and is used as three stacked 512x384 layers (see the
1058/10e0 docs):

| Layer | Rows | Use in these modules |
|---|---|---|
| 0 | 0..383 | What is presented to the window. Play area is y 20..286 (0x14, height 0x10b = 267). The status bar (HUD) is y 287..383. |
| 1 | 384..767 (`+0x180`) | Room composition ("work") layer: room background plus static objects. Sprites are erased by copying from here. The title saves its screen here. |
| 2 | 788..1054 (`+0x300`, play-field rows only; the buffer has 1055 rows) | Pristine room background (no objects), written by `1198:0234` as (0,404,512,267) → (0,788) (corrected per ARCHITECTURE.md §7.1 C2). |

Several draw hooks take a `layerDy` argument (0 or 0x180) saying which layer they draw into.

### 2.2 Input codes [O] (from `Input_GetCode`, 1028:0131)

Key codes are returned as-is: 0x0D Enter, 0x1B Esc (also returned when the window is closed),
0x20 Space, 0x13 Ctrl+S (WM_CHAR 0x13; WM_KEYDOWN maps only VK 0x21..0x2E, so the Pause key
produces nothing; corrected per ARCHITECTURE.md §7.1 C3). Mouse events over a registered hot spot return the hot-spot
id: left-button up = `id`, left down = `id|0x8000`, right down = `id|0x4000`, right up =
`id|0x2000`. Hot spot ids used here: 1200 (0x4B0, full play area or full screen) and 1033
(0x409, full screen, added by `Hud_SetClueBoxMode(1|2)`). So 0x4B0 / 0x409 = left click and
0x24B0 = right click.

### 2.3 Rooms

`g_room` (11b8:5cca, u8) is the current room 0..49; 0xFE means "climb over / start a new climb".
`g_rooms` (11b8:23d8) is an array of 50 `RoomDef` records of 28 bytes (§3.1). Rooms 0..8 are the
clubhouse, 9..22 mountain level 0, 23..35 level 1, 36..48 level 2, 49 the castle **[O]** (field
+0x1a/+0x1b values, §3.1). The term *climb* means one play-through from the bottom of the
mountain to the castle (other teams' term).

### 3.2 Spot slots: `kind` and `content` encoding

Each room has 3 *spots*, drawn as 118x133 object pictures at x = {26, 197, 368} (11b8:2dd4), y =
90 on screen (layer-1 y 0x1da) by 1198:0234 **[O]**.

`kind` (+0x14+i):

| Value | Meaning |
|---|---|
| 0..111 | Object picture = PMAP **1400+kind** (TMT256/TMT16); also the index into the attribute table OTHR 10555 (§3.4). **[O]** |
| 0xFD | Net-shop coin slot: no picture (the sign is drawn by 10f8:0285). **[O]** |
| 0xFE | Locked gate: no picture. **[O]** |
| 0xFF | No spot. **[O]** |

`content` (+0x17+i), tested by 10e0/1198 when a coin is tossed at the spot:

| Value | Meaning |
|---|---|
| 0 | Nothing (also written after a treasure or key is taken). **[O]** |
| 1 | No code path treats it differently from 0 (byte-scan of all code: reads only compare with 2, 3, 0xFD, 0xFE or `> 1`). **[O]** Purpose unknown (open question). |
| 2 | Treasure (gem): `Inv_CollectTreasure` 10e8:074a, then content := 0. **[O]** |
| 3 | The level's key: `Inv_SetHaveKey(1)` and hint 9, then content := 0. **[O]** |
| 0xFD | Net-shop coin slot: `g_shopCoinsLeft--`; at 0 the net door opens (10e0:07ad). **[O]** |
| 0xFE | Locked gate: needs the key, else hint 8 (10e0:0d18). Gates are in rooms 11, 25, 38 and lead to rooms 23, 36, 49. **[O]** |
| 0xFF | No spot. **[O]** |

Every layout record contains exactly one content 3 (key) **[O]**. Content counts over the 500
records x 18 spots of each tier resource **[O]**:

| Resource (tier) | content 0 | 1 | 2 (treasure) | 3 (key) |
|---|---|---|---|---|
| 10550 (0) | 5000 | 2500 | 1000 | 500 |
| 10551 (1) | 4000 | 3000 | 1500 | 500 |
| 10552 (2) | 3000 | 3500 | 2000 | 500 |
| 10553 (3) | 2000 | 4000 | 2500 | 500 |

### 3.4 Attribute table (OTHR 10555)

**[O]** 512 bytes = 128 entries of 4 bytes; entries 0..111 are used (112..127 are zero). Entry
`k` describes object picture 1400+k: `{u8 count (1..7); u8 size (0..4); u8 shape (0..4); u8
noun (1..15)}`. 0 means "attribute not applicable" (for example nouns 8 = acorn have shape 0).
Example: entry 0 = (1, 1, 1, 1) "one big round tree".

## 5. Segment 1100: climb layout and clues

### 5.1 `Layout_GenerateClimb()` 1100:04b5 [O]

Called by GameMain when a new climb starts (`g_room == 0xFE`).

```
for room in 0..49: for i in 0..2: rooms[room].kind[i] = 0xFF; rooms[room].content[i] = 0xFF;
Res_LoadToScratch(10550 + g_rankTier);               // scratch: u16 count; LayoutRec rec[count]
n  = *(i16*)scratch;
a  = (i32)rand() * n / 0x8000;                        // signed 32-bit multiply and divide
Layout_ApplyRecord(0, &rec[a]); g_clueFlags[0] = rec[a].flags; g_keyKind[0] = rec[a].keyKind;
do b = rand()*n/0x8000; while (b == a);
Layout_ApplyRecord(1, &rec[b]); g_clueFlags[1] = ...; g_keyKind[1] = ...;
do c = rand()*n/0x8000; while (c == a || c == b);
Layout_ApplyRecord(2, &rec[c]); g_clueFlags[2] = ...; g_keyKind[2] = ...;
Clue_ResolveAttributes();
```

`rand()` is Borland's LCG (seed = seed*0x015A4E35+1, returns (seed>>16)&0x7FFF), seeded by
GameMain with `srand(timeGetTime())` at every climb start. The record address is `scratch + 2 +
idx*0x26`.

### 5.2 `Layout_ApplyRecord(level, rec)` 1100:0000 (near) [O]

Straight-line stores implementing the table in §3.3: for each mapped layout spot `j`,
`rooms[r].kind[s] = rec[2+j]` and `rooms[r].content[s] = rec[0x14+j]`; for the gate slots both
bytes are set to 0xFE and for the net-shop slot both to 0xFD. `level` values other than 0..2 do
nothing.

### 5.3 `Clue_ResolveAttributes()` 1100:06cc (near) [O]

```
Res_LoadToScratch(10555);
for L in 0..2:
    t = scratch + g_keyKind[L]*4;            // {count, size, shape, noun}
    k = 0;
    if (g_clueFlags[L] & 8) g_clueAttr[L][k++] = t[0];
    if (g_clueFlags[L] & 4) g_clueAttr[L][k++] = t[1];
    if (g_clueFlags[L] & 2) g_clueAttr[L][k++] = t[2];
    if (g_clueFlags[L] & 1) g_clueAttr[L][k]   = t[3];   // no increment (last word)
    g_cluePlural[L] = (t[0] > 1);
```

With all four bits set the 4th store would spill into the next level; the data never sets all
four.

### 11.2 `QueueHint(event)` 1130:0000 [O]


## 18. Re-implementation notes

* **Climb set-up** = §5.1 to §5.4 run once per climb (and §5.4 again when a saved game is
  resumed). Keep the exact `rand()` formula if bit-exact layouts are wanted; otherwise any
  uniform choice of 3 distinct records from the tier's 500 works.
* The clue for level L is the 2 or 3 words of §5.4, displayed in the order count, size, shape,
  noun; the player earns them one at a time (`g_numClues`). The key is under the spot whose
  object kind equals `g_keyKind[L]`.
* **Net shop**: 4 coins tossed at the sign open the door; the player auto-walks to it, receives
  10 nets, and the door shows the empty niche for 4 frames (state 3 plus 3 waits) before closing.
* **Coin pile**: §7.2 exactly; it guarantees the game can never dead-lock when coins and nets
  are both 0.
* **Music**: the mapping of §10.1; music is restarted from the beginning after every hint and
  every Music-and-Sound toggle. Ctrl+S (corrected per ARCHITECTURE.md §7.1 C3) mutes and unmutes music, sound effects and voice
  together.
* **Hints**: one pending at a time; once-only bits are consumed when queued.
* **Title**: 100 ms animation ticks, 60 s page timeout, Enter/click next page, Space skip,
  Esc confirm quit; music OPEN1 then OPEN2.
* The empty hooks (1108, 1128:00ee) and the dead segment 1148 need no port.

## 19. Open questions

1. **Spot content 1**: about a quarter to two fifths of all layout spots have content 1, but no
   code reads it differently from 0. Was it a "coin under the object" feature of the Mac version,
   or is it read by code that Ghidra missed (a byte scan of all code segments found no other
   access to room offsets +0x17..+0x19)?
2. `RoomDef.+0x04/+0x05`, `+0x06..+0x11`: only the start position/frame/facing are used here; the
   meaning of the remaining fields belongs to the room/player document.
3. `GameDlg_RunModal` (10c0:0ae5) return values (1 = Yes, 0 = No, -1 = cancel) are now confirmed by the
   10c0 team's names file; the meaning of DlgDef +0x06 and +0x0c.. is still for the dialog
   document.
4. `MenuPopupDef` +0x04 (0x3f / 0x4e / 0x42) and +0x10/+0x12 (0x84,0x46 / 0x81,0x88 / 0x8f,0x01)
   are not read by `Menu_SetMenuBar`; their purpose (mnemonics? help ids?) is unknown.
5. `g_music4abe` (11b8:4abe) and `g_music5efd` (11b8:5efd) are written by `Music_PlayZone` and
   never read by any code found. They may be leftovers or read through a pointer.
6. Music zone -97 (TITLE.MID, 9009) and zones 2/4/6 have no caller in the exported code.
7. Hint event 1 has no caller in the exported code (events 0 and 2 are queued at every room start).
8. (Resolved by the 1150-1160 doc) `SignIn_Run` leaves the chosen player's saved state in the
   globals (`Users_LoadSelected`, which restores the saved `g_room`) or, for a new player,
   `Users_InitNewPlayer` sets `g_room = 0xFE` so GameMain starts a fresh climb. Whether a
   returning player whose saved `g_room` is 0xFE (climb finished) also gets a new layout follows
   from the same test.
9. (Resolved) `1178:0251(n)` is `Elf_SpawnForLevel(count)` per the 1168-1198 team, so
   {6, 8, 10, 12} is the number of elves per level by rank tier.
10. (Resolved by the 1058-1090 doc) `g_midiExtended` (11b8:4b76) selects the `E` (General MIDI)
    files, or the `B` (base FM synth) files for AdLib / "BASE" / "THUNDER BOARD" drivers.
11. `g_unk13cd` (11b8:13cd) values 0 / 1 / 0xFF are set around sign-in and puzzle code but never
    read; whether the Mac version had distinct sign-in music cues is unknown.
12. The `onEsc` callback contract of `Anim_PlayModal` (10d8:0082): after `MenuCmd_Exit` returns
    (the player answered No), does the animation continue or abort? This belongs to the 10d8
    document but affects how a port wires Esc during the end-of-climb celebration.
